How ChartSpec v1 decides a chart is valid

A new prototype turns a paragraph of product-requirements prose into an executable grammar for charts — and in doing so discovers that “validating a chart spec” is really two different jobs that the design had quietly merged into one.

What this page explains

The change is the untracked directory prototypes/chartspec-v1/ on branch research/python-arrow: a throwaway Pydantic draft of the ChartSpec v1 core grammar, plus a terminal harness that pushes it through fourteen cases. It is new code rather than an edit to existing code, so “before” in this page means either the prose specification it replaces, or an earlier state of the draft during the session that produced it. Both are labelled where they appear.

1. Background: why a chart needs a contract

chartagents is a Python library that turns a dataset and a sentence — “monthly revenue by region, last two years” — into a finished chart. The interesting design constraint is that a large language model is involved, and language models are not reliable enough to be trusted with the final answer.

The project's response is to split the work down the middle. Most requests, the team hypothesises around 80% of them, are ordinary: a bar chart, a line chart, a scatter plot. Those should travel a deterministic rail where the model's only job is to fill in a structured form, and ordinary trusted code renders the picture. The awkward remainder — a Sankey diagram, a hand-tuned annotation layout — travels a custom-code rail where the model writes real code that runs in a sandbox.

Definition · ChartSpec

The structured form the model fills in. It is a small, library-agnostic description of what the chart is — never how a particular library draws it. It is the contract between the planner that produces a chart and the renderer adapters that draw it, and it is the artifact that gets saved, versioned, diffed, and re-run.

Everything downstream leans on that contract. A saved ChartSpec is what makes a chart refreshable without spending a single token: when tomorrow's data arrives, the library re-runs the spec's data transformation and redraws, with no model call at all. It is also what the rail router inspects to decide which rail a request belongs on. So the question “is this spec valid?” is not a tidiness check. It is the gate that decides whether a chart can be drawn by trusted code.

What existed before

Until this prototype, ChartSpec existed only as eight bullet points in the requirements document. The relevant one reads, in full:

encodings — channels (x, y, color, size, facet, tooltip) each with field,
type (quantitative/temporal/ordinal/nominal), scale, axis config.
Deterministic encoding rules enforced at validation
(e.g., cardinality caps on color).

That is a perfectly reasonable paragraph. The prototype's job was to find out what it actually means when you have to type it out — and the most useful thing it found is hiding in that last line.

2. Intuition: one grammar, two kinds of wrong

Start with a spec that works. Here is the everyday case, revenue over time, split by region:

{
  "mark":  {"type": "bar", "stack": "stacked"},
  "encodings": {
    "x":     {"field": "month",       "type": "temporal"},
    "y":     {"field": "revenue_sum", "type": "quantitative"},
    "color": {"field": "region",      "type": "nominal"}
  }
}

A mark is the shape drawn on the page — bar, line, scatter. An encoding maps a column of data onto a visual channel: x position, y position, colour, size. The word channel is the standard term for “a visual property you can attach data to”, and the four types classify what kind of quantity a column holds: quantitative (a number you can average), temporal (a date), ordinal (ranked categories), nominal (unranked categories).

Now consider two specs that are wrong, and notice that they are wrong in genuinely different ways.

Wrong kind A — nonsense grammar

A histogram bins one column and counts how many rows fall in each bin. The counting is the chart's whole job, so supplying y is contradictory:

{"mark": {"type": "histogram"},
 "encodings": {
   "x": {"field": "revenue_sum", ...},
   "y": {"field": "count", ...}}}

You can see this is broken without looking at any data at all.

Wrong kind B — grammatical, but unrenderable

Colouring bars by product SKU. Structurally impeccable — color is a legal channel for bar, and nominal is a legal type:

{"mark": {"type": "bar"},
 "encodings": {
   "x": {"field": "month", ...},
   "color": {"field": "sku",
             "type": "nominal"}}}

But if sku has 830 distinct values, the chart is 830 colours of confetti. You cannot know that from the spec alone.

Two invalid specs. The left one violates the grammar. The right one satisfies the grammar and violates the data.

This is the finding. The requirements document said “deterministic encoding rules enforced at validation, e.g. cardinality caps on color”, as though cardinality caps were one more grammar rule. They cannot be. Cardinality — how many distinct values a column holds — is a property of the dataset, discovered by the profiler and written into a separate profile.json file. The spec never carries it. So the cap cannot possibly be checked when the spec is constructed.

Consequence · worth ratifying

Validation is two-phase, and only the first phase is a property of the grammar. Which means: a ChartSpec can be perfectly valid and still be unrenderable against a particular dataset. Those are different errors, they arrive at different times, and the planner should treat the second kind as feedback to repair rather than as a hard failure — “too many colours, try top-10 plus an other bucket” is a fixable note, not a dead end.

Phase 1 — grammar validation
ChartSpec.model_validate(raw) · needs only the spec · does the mark support these channels? are the types right? is the layer combination allowed?
a valid spec, e.g. bar / x=month / color=sku
Phase 2 — validation against the data profile
validate_against_profile(spec, profile) · needs profile.json · do the referenced columns exist? is sku's cardinality of 830 under the cap of 12?
a spec that is legal and drawable
Rail router
Compares the spec against the chosen renderer's declared capabilities and sends it down the deterministic or custom rail.

The validation pipeline. Each stage needs strictly more context than the one above it, which is why they cannot be collapsed: phase 1 runs the moment a spec is parsed, phase 2 only once a dataset has been profiled.

3. The code: how the rules are written down

The draft lives in one file, prototypes/chartspec-v1/chartspec_draft.py, and uses Pydantic — a Python library that turns class definitions into runtime validators. Declaring a field as int means Pydantic rejects a string at parse time. That gets the easy half of phase 1 for free; the interesting half is the rules Pydantic cannot express on its own.

Marks are objects, not names

The obvious way to model eight chart types is an enumeration of eight strings. The draft instead makes each mark a small object with a type discriminator (chartspec_draft.py:116):

chartspec_draft.py — the mark union
class BarMark(_MarkBase):
    type: Literal["bar"] = "bar"
    orientation: Literal["vertical", "horizontal"] = "vertical"
    stack: Literal["none", "stacked", "normalized"] = "none"

class PieMark(_MarkBase):
    type: Literal["pie"] = "pie"
    inner_radius_ratio: float = Field(default=0.0, ge=0.0, lt=1.0)  # > 0 => donut

Mark = Annotated[
    BarMark | LineMark | AreaMark | ScatterMark
    | PieMark | HeatmapMark | HistogramMark | BoxplotMark,
    Field(discriminator="type"),
]

The reason is that marks carry settings that belong nowhere else: whether bars stack, how many bins a histogram uses, which whisker convention a box plot follows. With a bare enum those settings have to be parked in a general-purpose style object, and style becomes the drawer where library-specific junk accumulates — precisely what a library-agnostic contract must avoid. A pleasant side effect: a donut is not a ninth mark, it is a pie with a hole (inner_radius_ratio > 0).

Definition · discriminated union

A union of several shapes where one field says which shape you have. Pydantic reads type: "pie" and validates against PieMark alone, so an inner_radius_ratio on a bar chart is rejected by name rather than silently ignored.

The per-mark contract is a table, not a pile of if statements

Which channels does each mark require, permit, and constrain? The draft answers with data (chartspec_draft.py:201) rather than branching code:

chartspec_draft.py — MARK_RULES (abridged)
MARK_RULES: dict[str, MarkRule] = {
    "bar": MarkRule(
        required=frozenset({"x", "y"}),
        allowed=frozenset({"x", "y", "color", "facet", "tooltip"}),
    ),
    "pie": MarkRule(
        required=frozenset({"color", "y"}),          # category + value
        allowed=frozenset({"color", "y", "tooltip"}),
        type_constraints={"color": _CAT, "y": _Q},
    ),
    "histogram": MarkRule(                            # y is COMPUTED, not supplied
        required=frozenset({"x"}),
        allowed=frozenset({"x", "color", "facet", "tooltip"}),
        type_constraints={"x": _Q},
    ),
    ...
}

Writing it as a table means the same structure can be read three ways: as the validator's input, as documentation of what each renderer must support, and as material for the prompt that teaches the planner what it is allowed to emit. Notice that pie takes its category on color and its value on y, rather than introducing a dedicated theta channel. That keeps the channel vocabulary at the six names the requirements document lists, at the cost of a mapping a reader has to learn once.

The checker that consumes the table (chartspec_draft.py:253) produces errors carrying machine-readable codes, so the planner's repair loop can branch on the code rather than parse English:

[E_MARK_CHANNEL_UNSUPPORTED] base: mark 'histogram' does not support
channel(s) ['y'] (histogram computes y itself — put the binned field on x)

Aggregation deliberately does not live on the channel

Anyone who has used Vega-Lite — the best-known grammar of this shape — will expect to write {"field": "revenue", "aggregate": "sum"} and let the encoding do the summing. The draft refuses (chartspec_draft.py:142). Encodings may only reference columns that the spec's transform block has already produced, which is why the examples say revenue_sum rather than revenue.

Two downstream commitments force this. First, when the data lives in a warehouse the transform is compiled to that warehouse's SQL and executed there — and SQL generation cannot reach up into the encodings to discover that something also needs summing. Second, zero-token refresh works by re-running the transform alone; if aggregation were split across two places, refresh would have to understand both. Keeping aggregation in exactly one place costs the planner some verbosity and buys a boundary that stays clean.

Layers, and a bug worth dwelling on

Real charts sometimes need two marks together: a line with point markers, bars with a target line across them. The draft models this as overlays on a base mark rather than a list of layers the base lives inside, so the single-mark majority stays flat, and bounds it three ways — a budget of two overlays, an explicit allowlist of permitted combinations, and one shared data transform.

The first version of the layer check contained a hole. It only validated a layer that supplied its own encodings; a layer that overrode nothing was skipped entirely. But such a layer still inherits all of the base chart's channels — and it might inherit one its own mark cannot draw. The case that exposed it: a scatter plot using size to show a third variable, with a trend line overlaid. Lines have no notion of size.

Before — the hole

if layer.encodings is not None:
    merged = ...
    _check_mark_channels(
        layer.mark.type, merged, ...)

A layer written as {"mark": {"type": "line"}} has encodings is None, so no check ran. The spec was accepted; the renderer would have to quietly drop the inherited size.

After — chartspec_draft.py:476

overrides = (layer.encodings.model_dump(
    exclude_none=True) if layer.encodings else {})
merged = Encodings.model_validate(
    {**self.encodings.model_dump(exclude_none=True),
     **overrides})
_check_mark_channels(
    layer.mark.type, merged, ...)

The merge now runs unconditionally, with an empty override set standing in for “inherits everything”. The spec is rejected up front.

The fix. The principle behind it: a spec that says one thing while the picture shows another is the exact failure the whole two-rail design exists to prevent, so it is cheaper to outlaw in the grammar than to catch later in the review gate.

…and the bug the fix uncovered

Tightening the check immediately rejected something that should obviously be legal: a line chart over time with point markers on it, which is about the commonest layered chart in existence. The scatter rule had demanded a quantitative x, and the inherited x was a date.

The rule was wrong, not the chart. A scatter plot against dates is perfectly ordinary on its own account, and mandatory for this overlay. So scatter now admits temporal positions (chartspec_draft.py:220) while still excluding categorical ones — because rejecting “scatter of region versus revenue”, which wants to be a bar chart, is the rule's entire value.

Trade-off

Every cell in the type table is a small bet. Too loose and the grammar waves nonsense through to the renderer; too tight and it silently outlaws a chart people legitimately want, which shows up only as unexplained traffic diverting to the expensive custom-code rail. The table needs a deliberate review against a corpus of real requests before anyone trusts the rail-share number.

Nothing means inherit

Every field on Style is optional, and None means inherit — never off (chartspec_draft.py:399). Resolution order at render time is: an explicit value in the spec, then the organisation's convention pack, then the theme, then the renderer's default.

This makes an anticipated feature disappear. Organisations were expected to need somewhere in the spec to hang their brand palette and house rules. They do not: they are simply one layer of the resolver, and a spec that sets nothing inherits the entire house style. One less thing in the grammar.

The same convention settles how a spec is serialised (chartspec_draft.py:489). Since absent and null say the same thing, canonical JSON omits nulls — otherwise one spec would have two valid encodings, and comparing two specs to compute a minimal edit would produce spurious differences. Round-tripping JSON → Pydantic → JSON is verified lossless on every accepted case in the harness.

Versioning

Specs are versioned MAJOR.MINOR with no patch component, because a patch release by definition cannot change the grammar, and a version component nothing may ever depend on is a liability. A renderer declares the newest grammar it understands; compatibility means the same major version and a minor no higher than the renderer's (chartspec_draft.py:507). Adding a mark or a channel bumps the minor and leaves old renderers working. Removing or reinterpreting one bumps the major and breaks them loudly, which is the point.

Running it

The harness, explore.py, is a menu of fourteen cases — valid specs, each category of invalid spec, and the version-compatibility matrix. It prints the canonical JSON and round-trip verdict for anything accepted, and the typed error for anything rejected. It needs no install step:

uv run prototypes/chartspec-v1/explore.py --all
Why a throwaway prototype earned its keep

None of the three findings on this page — the two-phase split, the inheritance hole, the over-tight scatter rule — were visible in the prose specification. Two of them only appeared because fixing the first one broke a case that had been passing. That is the argument for writing the executable draft before writing the real thing.
