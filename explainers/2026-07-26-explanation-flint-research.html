1. Background — the rail, the spec, and the prompt

If you have never seen this repository, three things are worth having in your head before the diff makes sense. None of them takes long.

What chartagents is trying to be

chartagents is a Python library that turns "monthly revenue by region, last two years" plus a data source into a finished chart, behind an API rather than inside a chat window. Its product document, chartagents-prd.md, organises the pitch as six pillars. Three of them matter for this diff:

  • Pillar 2 — data never leaves your infrastructure. Before any model is called, a profiler scans the data with DuckDB and emits a compact profile.json: schema, dtypes, cardinality, null rates, min/max/percentiles, a few sample rows. Only that metadata reaches the LLM.
  • Pillar 3 — engineered reliability. A deterministic rail handles the common majority of requests: the model emits a validated spec, and hand-written code renders it, with zero generated code in the path. Requests the grammar cannot express fall to a custom-code rail where the model writes Python or JavaScript in a sandbox.
  • Pillar 6 — generate once, refresh forever. A chart is a saved spec, so re-rendering it against tomorrow's data is a pure replay: re-run the stored transform, feed the renderer. No model call, no re-planning, $0 of inference.

↓ metadata only — this is all the model ever sees

What ChartSpec is, concretely

The spec is the contract between the model and the renderer: a small, library-agnostic grammar of graphics. A runnable draft lives at prototypes/chartspec-v1/chartspec_draft.py, marked PROTOTYPE — THROWAWAY, carrying nine numbered decisions D1–D9 that exist to be argued with. The piece this diff aims at is the Channel — one visual channel of the chart, such as the x axis or the colour:

prototypes/chartspec-v1/chartspec_draft.py:142–161

class Channel(BaseModel):
    model_config = ConfigDict(extra="forbid")
    field: str = Field(min_length=1)
    type: DataType
    title: str | None = None
    scale: ScaleSpec | None = None
    axis: AxisSpec | None = None
    sort: Literal["ascending", "descending", "none"] | str | None = None
    legend: bool | None = None  # color/size only; None => adapter default

and DataType, four values inherited from Vega-Lite:

prototypes/chartspec-v1/chartspec_draft.py:54–58

class DataType(StrEnum):
    QUANTITATIVE = "quantitative"
    TEMPORAL = "temporal"
    ORDINAL = "ordinal"
    NOMINAL = "nominal"
Definition — grammar of graphics

A way of describing a chart as data fields mapped onto visual channels (position, colour, size) rather than as drawing instructions. Vega-Lite is the best-known implementation; ChartSpec is a deliberately smaller dialect of the same idea, sized so that a hand-written renderer can implement all of it.

Where design knowledge currently comes from

Here is the crack the research widens. Look at two fields the draft already has:

prototypes/chartspec-v1/chartspec_draft.py:125–139

class ScaleSpec(BaseModel):
    ...
    zero: bool | None = None    # bar-baseline lint (§7.3 T1) reads this

class AxisSpec(BaseModel):
    ...
    format: str | None = None   # d3-format / strftime string

scale.zero records whether zero is meaningful on this axis — the review gate's Tier-1 lint reads it to decide whether a truncated bar baseline is a defect. axis.format is a raw d3-format string like "$,.2s". Both are declared, both are consumed, and nothing in the library computes either one. They arrive one way only: the planner prompt tells the model to fill them in, and the model does or does not.

The tension

Pillar 3 says design knowledge belongs in the library, so the deterministic rail can be trusted. But every decision that depends on what a number means — currency or percentage formatting, sum or average aggregation, sequential or diverging colour, whether a bar may start above zero — currently depends on the prompt, because quantitative does not carry enough meaning to derive any of them. The library declares the fields and then asks the model to be right.

What arrived from outside

In July 2026 Microsoft Research, with Renmin University, released microsoft/flint-chart under MIT: a visualization intermediate language plus a compiler. Its premise, as the research document reports it, is that low-level chart specs are "verbose, fragile, and error-prone," and that models are especially bad at managing them — so let the model state semantics and let a compiler derive the low-level settings.

Someone noticing this at exactly the moment ChartSpec's grammar is being frozen is what produced PR #13: first a deep read of Flint (commit e5af358), then — because Flint had nearly been missed entirely — a deliberate sweep for anything else in the same class (commit 2a0b4b9).

2. Intuition — a field called revenue

Take the smallest possible example. A table has a column revenue, US dollars, one row per month, and the user asks for a bar chart of it by month.

Today: the model authors the details

To get a good chart rather than a merely valid one, the planner has to emit not just the mapping but every presentational consequence of what a dollar amount is:

Today — the prompt has to know

{
  "mark": {"type": "bar"},
  "encodings": {
    "x": {"field": "month",
          "type": "temporal"},
    "y": {"field": "revenue_sum",
          "type": "quantitative",
          "scale": {"zero": true},
          "axis": {"format": "$,.2s"}}
  }
}

Proposed — the model states meaning

{
  "mark": {"type": "bar"},
  "encodings": {
    "x": {"field": "month",
          "type": "temporal",
          "semantic": "Date"},
    "y": {"field": "revenue_sum",
          "type": "quantitative",
          "semantic": "Revenue"}
  }
}
// zero + format derived, not authored

Figure 2. Same chart, two divisions of labour. On the left, four presentational facts are the model's responsibility and any of them can be silently wrong. On the right, one word — Revenue — is the model's responsibility, and a deterministic resolver derives currency formatting, a summing aggregation default, and a meaningful zero baseline from it.

The claim is not that the right-hand spec is shorter. It is that the right-hand spec is easier to be right about. A model that has never seen a d3-format string can still know that a column called revenue holds revenue. And once the library owns the derivation, the derivation is testable, reviewable, and identical on every run — which is exactly what "the deterministic rail" was supposed to mean.

The mechanism: a tiered vocabulary that degrades

The obvious objection is that a vocabulary of seventy type names is a new way for the model to be wrong. Flint's answer, as the document describes it, is a three-tier registry where every tier is a legal answer:

Tier 0 · 6Families — Temporal, Measure, Categorical… Fixes the fundamental encoding strategy. Cheap for a model to infer.
Tier 1 · 17Categories — Measure → Amount, Physical, Proportion, SignedMeasure. Distinct aggregation and formatting behaviour.
Tier 2 · 46Specific — Revenue ≠ Price (summable versus intensive); Temperature ≠ Quantity (a conditional diverging midpoint).

Resolution walks T2 → T1 → T0 and stops wherever the model got to. Say Revenue and you get currency formatting, a sum default, and a log-scale hint. Say only Amount and you still get currency and sum. Say only Measure and you still get quantitative with a meaningful zero. Say something unrecognised and you land on a generic quantitative fallback — which is precisely where the four-value DataType leaves you today. The floor of the new system is the ceiling of the old one.

Each type carries five orthogonal decision dimensions, and it is worth seeing them explicitly, because they are the list of prompt responsibilities the proposal is trying to retire:

DimensionValuesWhat it decides
Vis-encoding candidatespreference order over quantitative / ordinal / nominal / temporalwhich DataType to prefer
Aggregation roleadditive · intensive · signed-additive · dimension · identifierSUM versus AVG as the proposed default
Domain shapeopen · bounded · fixed · cyclicclamping, extrapolation, polar axes
Diverging naturenone · conditional · inherentsequential versus diverging palette
Format classcurrency · percent · unit-suffix · date …axis.format prefix, suffix, precision

Table 1. The five dimensions, as reported in docs/research/flint-chart-leverage.md §1. Compare against the fields in ScaleSpec and AxisSpec that no library code currently fills.

Why the same field can need two different answers

One detail is worth pausing on, because it explains why this is a resolver and not a lookup table. Consider a rating column bounded to [1, 5]. Put it on the x axis and the right answer is integer ticks at 1, 2, 3, 4, 5. Put it on colour and the right answer is a diverging palette with its midpoint at 3. Same field, same semantic type, different decision — because the channel differs.

So compilation is two-stage: stage one derives field-intrinsic properties (format, aggregation default, domain constraint) without knowing which channel will carry the field; stage two promotes those into channel-specific decisions. Per field, then per channel.

And the other half of the change: where Flint sits

The second claim of the document is about layering, and it is the reason the tone is opportunity rather than alarm. Flint compiles a spec into a polished native chart. That is the box in Figure 1 that chartagents has not built. Flint has no profiler, no planning loop, no review gate, no refresh guarantee, no data-source abstraction — and its MCP server serves the individual-in-a-chat persona the PRD lists as an explicit non-goal.

The mental model in one line

Flint stops exactly where chartagents' deterministic rail begins rendering. The document's framing: Cortex Analyst answers "what data"; Flint answers "given a spec, draw it well"; chartagents answers "given data and an instruction, decide the spec, guarantee its quality, and refresh it forever."

3.1 At the planner boundary — a new field on Channel

Option A, the document's highest-confidence recommendation, is one field:

proposed — docs/research/flint-chart-leverage.md §3

class Channel(BaseModel):
    field: str
    type: DataType                    # unchanged — still the 4-way Vega-Lite typing
    semantic: str | None = None       # NEW: "Revenue" | "Amount" | "Measure" | ...
    annotation: SemanticAnnotation | None = None   # intrinsicDomain / unit / sortOrder
    scale: ScaleSpec | None = None    # now fillable by the resolver
    axis: AxisSpec | None = None      # now fillable by the resolver
    ...

Note what is not proposed: DataType does not go away. The semantic type sits beside it and is optional, so every spec valid today stays valid. The annotation object handles the cases the type name alone cannot settle — that a rating's intrinsic domain is [1, 5], that a unit is °C rather than USD, that a category sorts small/medium/large rather than alphabetically.

3.2 Between profile and render — the resolver layer

The second half of Option A is where the derived values get filled in. The proposal puts a resolver between profile.json and the renderer, and — this is the load-bearing detail — declines to invent a new precedence concept for it. The draft already fixed one, in D8:

prototypes/chartspec-v1/chartspec_draft.py:399–410

class Style(BaseModel):
    """
    D8: every field is Optional and None means INHERIT, never "off".
    Precedence at render time: explicit spec value > org skill > theme > adapter default.
    """

Semantic-derived values become the adapter-default layer — the floor, not the ceiling:

Explicit spec value — the planner said format: "$,.0f"wins
Org skill — "always show revenue in thousands"then
Theme — house stylethen
Adapter default — derived from the semantic typefloor ← new

Figure 3. Option A adds a source of values, not a rule about them. A spec that sets nothing inherits sensible semantic defaults; anything an org or a planner states explicitly still wins, exactly as D8 already promised.

Invariant preserved

Because None means inherit everywhere in this grammar, and D9 excludes None from the canonical JSON form, a resolver that fills gaps at render time cannot change what a stored spec says. Spec-diffing for patch mode keeps working on the authored spec, not the resolved one.

3.3 Against D2 — a hint, not an authority

The most obvious way this proposal could have gone wrong is aggregation. Flint's types carry an aggregation role; ChartSpec has an explicit decision saying aggregation may not live on a channel:

prototypes/chartspec-v1/chartspec_draft.py:143–151

    D2: NO `aggregate` on the channel — unlike Vega-Lite.

    Encodings reference *output columns of the transform block*. Aggregation lives in
    `data.transform` (issue #4) because (a) pushdown compiles the transform to the
    source's SQL and cannot reach into encodings, and (b) zero-cost refresh (§7.7)
    re-runs the transform alone. Encoding-level aggregate would fork that boundary.

The document's resolution is a distinction with real consequences: the aggregation role is a default that seeds the transform planner ("Revenue implies propose SUM; Price implies propose AVG"), while data.transform remains the single source of truth about what was actually computed. Nothing in the render path or the pushdown path reads aggregation off a channel, so the boundary D2 protects — the transform is a self-contained thing that compiles to SQL and can be re-run alone — stays intact.

3.4 Against pillar 6 — freeze the inference at plan time

There is a subtler hazard, and the document catches it. Flint infers missing semantics from the data distribution: if 80% of a column's absolute values are ≤ 1, treat a percentage as fractional rather than as whole numbers. That heuristic is fine in a chat. It is dangerous under a refresh guarantee.

If inference re-ran on refresh

January's data: 92% of values ≤ 1 → read as fractional → axis shows 34%.

February's data drifts to 61% ≤ 1 → read as whole → the same chart now shows 0.34%. No error. No model call to blame. Silently different chart.

Pinned at plan time

The inference runs once, during planning, and its outcome is written into the spec as an annotation.

Every refresh replays the stored decision. New data cannot flip the reading, because nothing re-reads it.

Figure 4. Why the document insists distribution-based inference must be frozen into the spec rather than recomputed. Pillar 6's promise is that refresh is a replay; any heuristic that re-evaluates on new data quietly breaks that.

Note the direction of travel: semantic types strengthen the refresh guarantee rather than complicating it, because the resolution is deterministic and the inputs are stored in the spec. Two runs of the resolver over the same spec produce the same chart, which is what "bit-stable across runs" in pillar 3 requires.

3.5 Where validation would put it

The prototype's central finding was that validation cannot be one phase. Grammar checks run at construction; anything needing the data runs later:

Semantic resolution needs the profile — units, domains, distributions — so it lands naturally in phase 2, next to the cardinality caps that already live there. No new phase, no new plumbing.

3.6 The genuine edge — profiling beats guessing

This is the part of the document that is an argument rather than a summary, so it deserves to be stated precisely. Flint, running inside a chat, asks the model to infer semantic types and falls back to distribution heuristics. chartagents has already run DuckDB over the data before the model is called.

Flint in a chatmodel guesses the type → heuristics fill the gaps → compile
chartagentsDuckDB profile (cardinality, min/max, fractional-vs-whole, monotonic dates, currency-ish ranges) → seeds and validates the model's guess → resolver → compile

Figure 5. The same resolver, fed better inputs. The document's claim is parity plus a delta: signals Flint must infer heuristically, chartagents can compute — and can use to catch a model that typed a column wrong.

Open question, flagged in the document

How many of the 46 specific types can the profile actually determine on its own, and how many still need a model's guess? Nobody has measured this. It bounds how much planning the ontology really removes, and it is one of four questions the document hands off to tickets.

3.7 Option B — using Flint's compiler, and the reasons to be careful

The second option is heavier: compile ChartSpec → Flint's input → native chart, and get Vega-Lite, ECharts and Chart.js from one mapping instead of writing three renderers. The document rates this medium confidence and spends most of its length on the costs.

CostWhat it actually means here
Language boundaryThe three-backend compiler is TypeScript. flint-py is a native Python port but compiles Vega-Lite only and is source-only preview with no PyPI release. ECharts — the PRD's primary web output — would need a Node sidecar inside the sandbox, a port, or a bet on someone else's roadmap.
Grammar impedanceChartSpec carries things Flint's input does not model the same way: bounded overlay layers with a combo allowlist (D5), typed annotations, interactions flags, and the escape custom-rail marker. The mapping is lossy in both directions and needs a capability matrix before anyone commits.
GovernanceA young research artifact with no published roadmap. MIT licensing means the pieces can be vendored — which is itself a maintenance commitment, not a free escape.

The proposed shape of the experiment is what keeps this reversible: Flint would be one adapter behind the CapabilityProfile boundary the architecture already has, declaring a max_spec_version like any other. The version-compat helper for that already exists in the draft:

prototypes/chartspec-v1/chartspec_draft.py:507–516

def adapter_supports(spec_version: str, adapter_max: str) -> tuple[bool, str]:
    s_major, s_minor = (int(p) for p in spec_version.split("."))
    a_major, a_minor = (int(p) for p in adapter_max.split("."))
    if s_major != a_major:
        return False, f"[{SpecError.SPEC_VERSION_UNSUPPORTED}] spec major {s_major} != adapter major {a_major}"
    ...

An adapter is a pluggable thing that can be added or dropped without touching the planner, the router, or the review loop. Putting Flint there means the answer to "was this a good idea?" stays answerable later.

3.8 The second file — what else was out there

The landscape document exists because of an uncomfortable observation stated in its own header: Flint surfaced late and nearly got missed. So the sweep covers six categories. Five entries carry actions:

Draco / Draco 2 (UW)viz-design knowledge as constraints

Formalises design guidelines as hard constraints (prune ill-formed encodings) and soft constraints with learned weights (rank the rest). The document maps these onto two existing chartagents parts.

chat2plotPython · MIT

The closest shipped precedent for the central bet: the LLM emits a validated pydantic/JSON spec, not code. Its failure taxonomy is a free corpus of valid-but-wrong specs to test validators against.

LIDA (Microsoft)agentic pipeline, code-gen

Summarise → goal → generate code → self-evaluate → repair. The well-executed version of what the PRD positions against. A reviewer will ask "how is this not just LIDA?" and the PRD does not name it.

Vizro-AI → Vizro-MCPMcKinsey

Deprecated AI dashboard generation, retreated to chart-only plus an MCP server. Read as a signal about scope discipline — and as evidence the field went MCP-first while chartagents went API-first.

Evidence · Rill · MalloyBI-as-code

Durable, versionable, cheap-to-refresh specs — pillar 6's pattern, already validated. The delta to state plainly: their specs are human-authored, chartagents' are agent-authored and quality-gated.

Spec Score · Vision Scoreevaluation

Named metrics for the §11 benchmark. Spec Score is judge-free and deterministic — a structural answer to the LLM-judge self-preference risk the PRD already worries about.

The Draco entry is the one that echoes the Flint argument most exactly, and it lands on code that already exists. The prototype's per-mark channel contract is a hand-rolled table of hard constraints:

prototypes/chartspec-v1/chartspec_draft.py:220–233

    "scatter": MarkRule(
        required=frozenset({"x", "y"}),
        allowed=frozenset({"x", "y", "color", "size", "facet", "tooltip"}),
        type_constraints={
            "x": frozenset({DataType.QUANTITATIVE, DataType.TEMPORAL}),
            "y": frozenset({DataType.QUANTITATIVE, DataType.TEMPORAL}),
            "size": _Q,
        },
    ),
    "pie": MarkRule(
        required=frozenset({"color", "y"}),
        allowed=frozenset({"color", "y", "tooltip"}),
        type_constraints={"color": _CAT, "y": _Q},
    ),

Draco's hard constraints are the same idea, expressed formally and far more completely. Its soft constraints — colourblind safety, cardinality caps, the bar-baseline rule — are the Tier-1 lint gate in another notation. The recommendation is deliberately modest: borrow the model and the hard/soft taxonomy, do not take on an Answer Set Programming solver as a runtime dependency of an embeddable library.

Nothing in any code path. That is worth saying plainly, because the documents read like instructions and are not. What merging did is make four proposals reviewable:

Explicit non-actions

Do not make Flint a hard dependency of the core. Do not route the primary ECharts output through a Node sidecar before the Vega-Lite spike proves the mapping is clean. Do not embed Draco's solver. Do not pivot to MCP-first. And do not frame Flint as a competitor, internally or externally — the USP was never the renderer.

What this page does not verify
