1. Background: why a chart needs a contract

chartagents is a Python library. It gets a data set and a sentence, for example "monthly revenue by region, last two years". It then makes a finished chart.

A language model does part of this work. But a language model is not sufficiently reliable to make the final chart. Because of this, the design divides the work into two paths.

  • The deterministic rail. Most requests are usual requests: a bar chart, a line chart, or a scatter plot. The team estimates that these are approximately 80% of all requests. On this rail, the language model only fills in a structured form. Trusted code then draws the chart.
  • The custom-code rail. The other requests are unusual. Two examples are a Sankey diagram and a hand-tuned annotation layout. On this rail, the language model writes code, and a sandbox runs that code.
Definition · ChartSpec

The ChartSpec is the structured form that the language model fills in. It is a small description of what the chart is. It does not say how one chart library draws the chart. The system saves the ChartSpec, gives it a version, compares it with other ChartSpecs, and runs it again.

All the later steps use this contract. A saved ChartSpec makes a refresh possible at no token cost. When new data arrives, the library runs the transform block again and draws the chart again. It does not call the language model. The rail router also reads the ChartSpec to select the rail. So the question "is this ChartSpec valid?" is not a small quality check. It is the gate that lets trusted code draw the chart.

What was there before

Before this prototype, the ChartSpec was only eight bullet points in the requirements document. This is the related bullet point, in full:

encodings — channels (x, y, color, size, facet, tooltip) each with field,
type (quantitative/temporal/ordinal/nominal), scale, axis config.
Deterministic encoding rules enforced at validation
(e.g., cardinality caps on color).

The text is correct, but it is short. The task of the prototype was to find the full meaning of this text. The most important result is in the last line of the text.

2. The idea: one grammar, two types of error

First, look at a ChartSpec that is correct. It shows revenue with time, and it divides the revenue by region:

{
  "mark":  {"type": "bar", "stack": "stacked"},
  "encodings": {
    "x":     {"field": "month",       "type": "temporal"},
    "y":     {"field": "revenue_sum", "type": "quantitative"},
    "color": {"field": "region",      "type": "nominal"}
  }
}

The four data types classify what a column holds:

  • quantitative — a number. You can calculate a mean value from it.
  • temporal — a date or a time.
  • ordinal — categories in a known sequence.
  • nominal — categories with no sequence.

Now look at two ChartSpecs that are not correct. The two errors are different types of error.

Error type A — the grammar is wrong

A histogram puts one column into bins. It then counts the rows in each bin. The count is the task of the chart, so a y channel is a contradiction:

{"mark": {"type": "histogram"},
 "encodings": {
   "x": {"field": "revenue_sum", ...},
   "y": {"field": "count", ...}}}

You can find this error with no data.

Error type B — the grammar is correct, but no renderer can draw the chart

This ChartSpec gives a color to each bar, by product SKU. The structure is correct. color is a legal channel for a bar mark, and nominal is a legal data type:

{"mark": {"type": "bar"},
 "encodings": {
   "x": {"field": "month", ...},
   "color": {"field": "sku",
             "type": "nominal"}}}

But if the sku column holds 830 different values, the chart shows 830 colors. You cannot find this error from the ChartSpec alone.

Figure 1. Two ChartSpecs that are not valid. The ChartSpec on the left disobeys the grammar. The ChartSpec on the right obeys the grammar and disagrees with the data.

This is the result of the prototype. The requirements document puts the cardinality cap with the grammar rules. That is not possible. Cardinality is a property of the data. The profiler measures it and writes it into profile.json. The ChartSpec never holds it. So a check of the cap at construction time is not possible.

Result · agree to this before you continue

Validation has two phases. Only the first phase is a property of the grammar. Thus a ChartSpec can be fully valid, but no renderer can draw it with one specified data set.

These are different errors, and they occur at different times. The planner must use the second error as data for a repair, not as a permanent failure. The message "there are too many colors, use the first 10 values and one other group" tells the planner how to correct the ChartSpec.

Phase 1 — grammar validation ChartSpec.model_validate(raw) · needs the ChartSpec only · Does the mark support these channels? Are the data types correct? Is this combination of layers permitted?
↓ a valid ChartSpec, for example bar / x=month / color=sku
Phase 2 — validation against the profile validate_against_profile(spec, profile) · needs profile.json · Do the columns exist? Is the cardinality of sku, which is 830, below the cap of 12?
↓ a ChartSpec that is legal and possible to draw
Rail router Compares the ChartSpec with the capabilities of the selected renderer adapter. Then sends the request to the deterministic rail or to the custom-code rail.

Figure 2. The validation pipeline. Each stage needs more data than the stage above it. This is why you cannot make one stage from the two. Phase 1 runs when the system reads a ChartSpec. Phase 2 runs only after the profiler measures a data set.

3. The code: how the rules are written

The prototype is one file, prototypes/chartspec-v1/chartspec_draft.py. It uses Pydantic. Pydantic is a Python library that changes a class definition into a validator that runs at run time. If you declare a field as int, Pydantic rejects a string. This gives the easy half of phase 1 at no cost. The other half is the set of rules that Pydantic cannot express alone.

3.1 Marks are objects, not names

The usual method is one list of eight strings, one string for each chart type. The prototype uses a different method. Each mark is a small object with a type field that identifies it (chartspec_draft.py:116):

chartspec_draft.py — the mark union

class BarMark(_MarkBase):
    type: Literal["bar"] = "bar"
    orientation: Literal["vertical", "horizontal"] = "vertical"
    stack: Literal["none", "stacked", "normalized"] = "none"

class PieMark(_MarkBase):
    type: Literal["pie"] = "pie"
    inner_radius_ratio: float = Field(default=0.0, ge=0.0, lt=1.0)  # > 0 => donut

Mark = Annotated[
    BarMark | LineMark | AreaMark | ScatterMark
    | PieMark | HeatmapMark | HistogramMark | BoxplotMark,
    Field(discriminator="type"),
]

Each mark has settings that no other mark uses. Bars stack or do not stack. A histogram has a number of bins. A box plot has a whisker convention. A list of strings has no location for these settings. Then you must put them in a general style object, and that object collects settings that apply to one chart library only. A library-agnostic contract must prevent this.

There is also a good secondary result. A donut is not a ninth mark. A donut is a pie mark with a hole, which is inner_radius_ratio > 0.

Definition · discriminated union

A set of possible shapes, where one field tells you which shape you have. Pydantic reads type: "pie" and then validates against PieMark only. Thus Pydantic rejects an inner_radius_ratio field on a bar mark. It does not ignore that field.

3.2 The contract for each mark is a table

Which channels does each mark require, permit, and constrain? The prototype gives the answer as data (chartspec_draft.py:201). It does not use if statements:

chartspec_draft.py — MARK_RULES (short form)

MARK_RULES: dict[str, MarkRule] = {
    "bar": MarkRule(
        required=frozenset({"x", "y"}),
        allowed=frozenset({"x", "y", "color", "facet", "tooltip"}),
    ),
    "pie": MarkRule(
        required=frozenset({"color", "y"}),          # category + value
        allowed=frozenset({"color", "y", "tooltip"}),
        type_constraints={"color": _CAT, "y": _Q},
    ),
    "histogram": MarkRule(                            # the code computes y
        required=frozenset({"x"}),
        allowed=frozenset({"x", "color", "facet", "tooltip"}),
        type_constraints={"x": _Q},
    ),
    ...
}

A table has three uses at the same time:

  • The validator reads it as input.
  • A person reads it as the specification of what each renderer adapter must support.
  • The prompt builder reads it to tell the planner what it can emit.

Note the rule for pie. The category goes on color and the value goes on y. There is no special theta channel. This keeps the number of channel names at six, which is the number in the requirements document. The cost is that each reader must learn this map one time.

The checker that reads the table (chartspec_draft.py:253) writes errors with a code. The repair loop in the planner can then test the code. It does not parse English:

[E_MARK_CHANNEL_UNSUPPORTED] base: mark 'histogram' does not support
channel(s) ['y'] (histogram computes y itself — put the binned field on x)

3.3 Aggregation is not on the channel

Vega-Lite is the best known grammar of this type. In Vega-Lite you write {"field": "revenue", "aggregate": "sum"}, and the encoding does the addition. The prototype does not permit this (chartspec_draft.py:142). An encoding can point only to a column that the transform block made. This is why the examples on this page use revenue_sum and not revenue.

Two later requirements make this necessary:

  • Warehouse pushdown. If the data is in a warehouse, the system compiles the transform block to the SQL of that warehouse and runs it there. The SQL generator reads the transform block. It cannot read the encodings.
  • Refresh at no token cost. A refresh runs the transform block again, and it does nothing else. If aggregation were in two places, a refresh would have to read both.

Aggregation in one place only makes the ChartSpec longer. But it also keeps the boundary between the transform block and the encodings clean.

3.4 Layers, and one important defect

Some charts need two marks together. Two examples are a line with point markers, and bars with a target line across them. The prototype models this as overlays on a base mark. It does not model this as a list of layers that contains the base mark. Thus the usual chart, which has one mark, stays flat. The prototype puts three limits on overlays: a maximum of two overlays, a list of permitted combinations, and one shared transform block.

The first version of the layer check had a hole. It validated a layer only if that layer supplied its own encodings. It did not validate a layer that supplied no encodings. But such a layer inherits all the channels of the base mark. One of those channels can be a channel that the mark of the layer cannot draw. The example that showed the defect is a scatter plot. It uses size for a third variable, and it has a trend line on top of it. A line mark has no size.

Before — the hole

if layer.encodings is not None:
    merged = ...
    _check_mark_channels(
        layer.mark.type, merged, ...)

A layer written as {"mark": {"type": "line"}} has encodings is None. So no check ran. The system accepted the ChartSpec. Then the renderer adapter had to discard the inherited size channel without a message.

After — chartspec_draft.py:476

overrides = (layer.encodings.model_dump(
    exclude_none=True) if layer.encodings else {})
merged = Encodings.model_validate(
    {**self.encodings.model_dump(exclude_none=True),
     **overrides})
_check_mark_channels(
    layer.mark.type, merged, ...)

The merge now runs for every layer. An empty set of overrides has the meaning "this layer inherits all channels". The system rejects the ChartSpec immediately.

Figure 3. The correction. A ChartSpec that says one thing while the chart shows a different thing is the primary failure. The two-rail design exists to prevent this failure. It costs less to prevent this failure in the grammar than to find it later in the review gate.

3.5 The defect that the correction found

The stronger check immediately rejected a chart that must be legal. That chart is a line chart against time with point markers on it, which is a very common layered chart. The rule for scatter required a quantitative x channel. But the inherited x channel held a date.

The rule was wrong. The chart was correct. A scatter plot against dates is a usual chart, and this overlay requires it. So scatter now permits temporal positions (chartspec_draft.py:220). It continues to reject categorical positions, because that rejection is the value of the rule. A "scatter plot of region against revenue" must be a bar chart.

Trade-off

Each cell in the table of data types is a small risk. If a cell is too permissive, the grammar sends incorrect charts to the renderer adapter. If a cell is too strict, the grammar rejects a chart that users want. A strict cell is difficult to find, because the only symptom is more traffic on the expensive custom-code rail. A person must examine the table against a set of real requests before the team uses the estimate of 80%.

3.6 None has the meaning "inherit"

Each field on Style is optional. The value None has the meaning inherit. It does not have the meaning off (chartspec_draft.py:399). At render time, the resolver reads four sources in this sequence:

  • an explicit value in the ChartSpec;
  • then the convention pack of the organization;
  • then the theme;
  • then the default of the renderer adapter.

This removes a feature that the team expected to build. The team thought that each organization needs a location in the ChartSpec for its brand palette and its house rules. It does not. These are one layer of the resolver. A ChartSpec that sets no style value gets the full house style. The grammar is smaller as a result.

The same rule controls the JSON form (chartspec_draft.py:489). An absent field and a null field have the same meaning. So the canonical JSON form removes all nulls. If it did not, one ChartSpec would have two valid JSON forms. Then a comparison of two ChartSpecs, which computes the smallest possible edit, would report differences that are not real. The harness tests the sequence JSON → Pydantic → JSON on each accepted case. No case loses data.

3.7 Versions

A ChartSpec has a version with the form MAJOR.MINOR. There is no patch component, because a patch release cannot change the grammar. A version component that nothing can use is a risk.

Each renderer adapter declares the most recent grammar that it can read. A ChartSpec is compatible with that adapter if two conditions are true (chartspec_draft.py:507). The major versions must be equal. The minor version of the ChartSpec must not be higher than the minor version of the adapter. A new mark or a new channel increases the minor version, and old adapters continue to operate. A mark or a channel that you remove or change increases the major version, and old adapters stop with an error. This error is the correct result.

3.8 How to run the prototype

The harness is explore.py. It is a menu of fourteen cases: valid ChartSpecs, one case for each class of invalid ChartSpec, and the version compatibility matrix. For each accepted case it prints the canonical JSON and the result of the round-trip test. For each rejected case it prints the error with its code. You do not have to install it:

uv run prototypes/chartspec-v1/explore.py --all
Why this throwaway prototype was worth the time

The prototype found three results: the two phases of validation, the hole in the layer check, and the scatter rule that was too strict. None of the three results was visible in the text of the requirements document. Two of the three became visible only because the correction of the first result caused a failure in a case that passed before. This is the argument to write the executable draft before you write the real code.
