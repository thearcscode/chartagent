Most explainer pages describe new code. This page does not. Pull request #13 adds no code to chartagent. It adds two Markdown files, and nothing in the repository reads a Markdown file. But the repository is still in its design phase. The product of the work is a set of decisions, and these two files move some of those decisions.

So this page answers a different question. It answers: which decisions does this change open, what is the result if the team takes them, and what in the prototype must change?

1. Background — the rail, the ChartSpec, and the prompt

If this repository is new to you, three facts make the change easier to read.

1.1 What chartagents must become

chartagents is a Python library. It gets a data source and an instruction, for example "monthly revenue by region, last two years". It then makes a finished chart. It operates behind an API. It does not operate in a chat window.

The product document, chartagents-prd.md, has six pillars. Three of them apply here:

  • Pillar 2 — the data stays in your infrastructure. Before the first call to the language model, the profiler reads the data with DuckDB. It writes a small profile.json file. That file holds the schema, the data types, the cardinality, the null rates, the minimum and maximum values, the percentiles, and some sample rows. The language model gets this metadata only.
  • Pillar 3 — reliability by design. The deterministic rail does most requests. The language model emits a ChartSpec, the system validates it, and trusted code draws the chart. There is no generated code on this path. A request that the grammar cannot express goes to the custom-code rail, where the language model writes Python or JavaScript in a sandbox.
  • Pillar 6 — make the chart one time, refresh it many times. A chart is a saved ChartSpec. To draw it again with new data, the system runs the stored transform block again and then calls the renderer adapter. There is no call to the language model, and the token cost is zero.

1.2 What the ChartSpec is

The ChartSpec is the contract between the language model and the renderer adapter. It is a small grammar of graphics, and it is independent of any chart library. A runnable draft is at prototypes/chartspec-v1/chartspec_draft.py. That file has the mark PROTOTYPE — THROWAWAY. It holds nine numbered decisions, D1 to D9, and each decision exists for the team to examine.

This change is about the Channel class. A channel is one visual property of the chart, for example the x axis or the color:

prototypes/chartspec-v1/chartspec_draft.py:142–161

class Channel(BaseModel):
    model_config = ConfigDict(extra="forbid")
    field: str = Field(min_length=1)
    type: DataType
    title: str | None = None
    scale: ScaleSpec | None = None
    axis: AxisSpec | None = None
    sort: Literal["ascending", "descending", "none"] | str | None = None
    legend: bool | None = None  # color/size only; None => adapter default

The DataType class holds four values. They come from Vega-Lite:

prototypes/chartspec-v1/chartspec_draft.py:54–58

class DataType(StrEnum):
    QUANTITATIVE = "quantitative"
    TEMPORAL = "temporal"
    ORDINAL = "ordinal"
    NOMINAL = "nominal"
Definition · grammar of graphics

A method to describe a chart as data columns that map onto visual channels, for example position, color, and size. It does not describe a chart as a sequence of drawing commands. Vega-Lite is the best known example. The ChartSpec is a smaller dialect of the same idea. Its size lets one team write a renderer adapter that supports all of it.

1.3 Where the design knowledge comes from today

This is the problem that the research examines. Look at two fields that the prototype already has:

prototypes/chartspec-v1/chartspec_draft.py:125–139

class ScaleSpec(BaseModel):
    ...
    zero: bool | None = None    # the bar-baseline lint (§7.3 T1) reads this

class AxisSpec(BaseModel):
    ...
    format: str | None = None   # a d3-format or strftime string

The scale.zero field records if zero has a meaning on this axis. The tier 1 lint in the review gate reads it. It then decides if a bar that starts above zero is a defect. The axis.format field holds a d3-format string, for example "$,.2s". The prototype declares both fields, and other code reads both fields. But no code in the library computes either field. They have one source only. The prompt tells the language model to supply them, and the model supplies them or does not.

The conflict

Pillar 3 says that the design knowledge belongs in the library, because that makes the deterministic rail reliable. But each decision that depends on the meaning of a number depends on the prompt today. Four examples are currency format, percentage format, the choice between a sum and a mean value, and the choice between a sequential palette and a diverging palette. The value quantitative does not hold sufficient meaning to compute any of them. So the library declares the fields and then asks the model to be correct.

1.4 What arrived from outside

In July 2026, Microsoft Research and Renmin University released microsoft/flint-chart under the MIT license. It is an intermediate language for charts, and a compiler for that language. The research document reports its premise: low-level chart specs are long, weak, and easy to get wrong, and language models are bad at these specs. So the model must state the meaning, and a compiler must compute the low-level settings.

A person found Flint at the same time as the team started to freeze the ChartSpec grammar. That is the reason for pull request #13. The pull request has two commits. The first commit (e5af358) is a deep read of Flint. The team nearly missed Flint, so the second commit (2a0b4b9) is a deliberate search for other libraries of the same class.

2. The idea — a column with the name revenue

Use the smallest possible example. A table has a column with the name revenue. The values are US dollars, and there is one row for each month. The user asks for a bar chart of the revenue by month.

2.1 Today: the language model supplies the details

A valid chart is not sufficient. To get a good chart, the planner must emit two things. It must emit the map from columns to channels. It must also emit each presentation value that follows from the meaning of a dollar amount:

Today — the prompt must know this

{
  "mark": {"type": "bar"},
  "encodings": {
    "x": {"field": "month",
          "type": "temporal"},
    "y": {"field": "revenue_sum",
          "type": "quantitative",
          "scale": {"zero": true},
          "axis": {"format": "$,.2s"}}
  }
}

Proposed — the model states the meaning

{
  "mark": {"type": "bar"},
  "encodings": {
    "x": {"field": "month",
          "type": "temporal",
          "semantic": "Date"},
    "y": {"field": "revenue_sum",
          "type": "quantitative",
          "semantic": "Revenue"}
  }
}
// the resolver computes zero and format

Figure 2. One chart, two divisions of the work. On the left, the model is responsible for four presentation values, and each one can be wrong. On the right, the model is responsible for one word, Revenue. A resolver then computes the currency format, the default aggregation, and the zero baseline.

The claim is not that the ChartSpec on the right is shorter. The claim is that it is easier to get correct. A model that has never read a d3-format string can still know that a column with the name revenue holds revenue. And when the library owns the computation, that computation is testable, a person can review it, and it gives the same result on each run. This is the meaning of the term "deterministic rail".

2.2 The mechanism: three tiers of vocabulary

There is an obvious objection. A vocabulary of seventy type names is a new method for the model to be wrong. The document reports the answer from Flint. The registry has three tiers, and each tier is a legal answer:

Tier 0 · 6Families — Temporal, Measure, Categorical, and three more. They set the basic encoding strategy. A model can select one at a low cost.
Tier 1 · 17Categories — for example Measure divides into Amount, Physical, Proportion, and SignedMeasure. Each one has different aggregation and format behavior.
Tier 2 · 46Specific types — Revenue is not Price, because you can add revenue but you must not add a price. Temperature is not Quantity, because temperature can have a diverging midpoint.

The resolver reads tier 2, then tier 1, then tier 0. It stops at the tier that the model supplied. The result is a sequence of smaller answers:

  • Say Revenue, and you get the currency format, a sum as the default aggregation, and a hint for a log scale.
  • Say Amount, and you get the currency format and the sum.
  • Say Measure, and you get a quantitative encoding with a meaningful zero.
  • Say a word that the registry does not know, and you get the generic quantitative result.

That last result is the same result that the four-value DataType class gives today. The lowest result of the new system is the highest result of the old system.

Each semantic type carries five independent dimensions. This list is important, because it is the list of prompt responsibilities that the proposal removes:

DimensionValuesWhat it decides
Encoding candidatesa preference sequence over quantitative, ordinal, nominal, and temporalwhich DataType value to prefer
Aggregation roleadditive · intensive · signed-additive · dimension · identifierSUM or AVG as the proposed default
Domain shapeopen · bounded · fixed · cyclicclamp limits, extrapolation, polar axes
Diverging naturenone · conditional · inherenta sequential palette or a diverging palette
Format classcurrency · percent · unit-suffix · date, and morethe prefix, the suffix, and the precision in axis.format

Table 1. The five dimensions, as docs/research/flint-chart-leverage.md §1 reports them. Compare them with the fields in ScaleSpec and AxisSpec that no library code fills today.

2.3 Why one column can need two different answers

One detail explains why this is a resolver and not a lookup table. Take a rating column with a domain of 1 to 5. Put it on the x axis, and the correct answer is integer ticks at 1, 2, 3, 4, and 5. Put it on the color channel, and the correct answer is a diverging palette with its midpoint at 3. The column is the same and the semantic type is the same, but the decision is different, because the channel is different.

So the compiler has two stages. Stage one computes the properties of the column: the format, the default aggregation, and the domain limits. It does not know which channel gets the column. Stage two changes those properties into decisions for one channel. First for each column, then for each channel.

2.4 The second claim: where Flint belongs

The second claim of the document is about layers, and it is the reason for the positive tone. Flint compiles a spec into a good native chart. That is the box in Figure 1 that the team has not built. Flint has no profiler, no planning loop, no review gate, no refresh guarantee, and no data source abstraction. Its MCP server also serves the single person in a chat window, and the product document lists that person as an explicit non-goal.

The model in one line

Flint stops at the exact point where the deterministic rail of chartagents starts to render. The document states it like this. Cortex Analyst answers "which data". Flint answers "I have a spec, draw it well". chartagents answers "I have data and an instruction, select the spec, guarantee its quality, and refresh it for ever".

3.1 At the planner boundary — a new field on Channel

Option A is the recommendation with the highest confidence. It is one new field:

proposed — docs/research/flint-chart-leverage.md §3

class Channel(BaseModel):
    field: str
    type: DataType                    # no change — the 4 Vega-Lite values stay
    semantic: str | None = None       # NEW: "Revenue" | "Amount" | "Measure" | ...
    annotation: SemanticAnnotation | None = None   # intrinsicDomain / unit / sortOrder
    scale: ScaleSpec | None = None    # the resolver can now fill this
    axis: AxisSpec | None = None      # the resolver can now fill this
    ...

Note what the proposal does not do. The DataType class stays. The semantic type is beside it, and the semantic type is optional. So each ChartSpec that is valid today stays valid. The annotation object holds the facts that a type name alone cannot give. Three examples follow:

  • the domain of a rating is 1 to 5;
  • the unit is °C and not USD;
  • the category sorts in the sequence small, medium, large, and not in alphabetical sequence.

3.2 Between the profile and the render — the resolver

The second half of Option A puts the computed values into the chart. The proposal puts a resolver between profile.json and the renderer adapter. Then, and this is the important detail, the proposal refuses to invent a new precedence rule for it. The prototype already fixed a precedence rule in decision D8:

prototypes/chartspec-v1/chartspec_draft.py:399–410

class Style(BaseModel):
    """
    D8: every field is Optional and None means INHERIT, never "off".
    Precedence at render time: explicit spec value > org skill > theme > adapter default.
    """

The values from the semantic type become the adapter default layer. That layer is the floor, not the ceiling:

Explicit value in the ChartSpec — the planner wrote format: "$,.0f"wins
Organization skill — "always show revenue in thousands"then
Theme — the house stylethen
Adapter default — computed from the semantic typefloor ← new

Figure 3. Option A adds a source of values. It does not add a rule about them. A ChartSpec that sets no value gets good defaults. A value that an organization or a planner states explicitly still wins, which is what D8 already promises.

The invariant stays true

In this grammar, None has the meaning inherit in each position. Decision D9 removes each None from the canonical JSON form. So a resolver that fills the empty fields at render time cannot change what a stored ChartSpec says. Patch mode continues to compare the ChartSpec that the planner wrote. It does not compare the resolved ChartSpec.

3.3 Against D2 — a hint, not an authority

Aggregation is the most probable failure of this proposal. The Flint types carry an aggregation role. But the ChartSpec has an explicit decision that forbids aggregation on a channel:

prototypes/chartspec-v1/chartspec_draft.py:143–151

    D2: NO `aggregate` on the channel — unlike Vega-Lite.

    Encodings reference *output columns of the transform block*. Aggregation lives in
    `data.transform` (issue #4) because (a) pushdown compiles the transform to the
    source's SQL and cannot reach into encodings, and (b) zero-cost refresh (§7.7)
    re-runs the transform alone. Encoding-level aggregate would fork that boundary.

The document gives a distinction with a real result. The aggregation role is a default that seeds the transform planner. Revenue proposes SUM, and Price proposes AVG. The data.transform block stays the only source of truth about the computation. No code in the render path or the pushdown path reads an aggregation from a channel. So the boundary that D2 protects stays intact. That boundary makes the transform block a self-contained thing that compiles to SQL and that the system can run alone.

3.4 Against pillar 6 — freeze the inference at plan time

There is a less obvious hazard, and the document finds it. Flint computes a missing semantic type from the distribution of the data. For example, if 80% of the absolute values in a column are 1 or less, Flint reads a percentage as a fraction and not as a whole number. That method is acceptable in a chat. It is dangerous with a refresh guarantee.

If the inference runs again on each refresh

The data for January: 92% of the values are 1 or less. Flint reads a fraction. The axis shows 34%.

The data for February moves to 61%. Flint reads whole numbers. The same chart now shows 0.34%. There is no error and no call to the language model. The chart is different, and nothing reports it.

Pinned at plan time

The inference runs one time, during the planning step. The system writes the result into the ChartSpec as an annotation.

Each refresh replays the stored decision. New data cannot change the reading, because no code reads it again.

Figure 4. Why the document says that the system must freeze a distribution-based inference into the ChartSpec. Pillar 6 promises that a refresh is a replay. A method that runs again on new data breaks that promise, and it gives no warning.

Note the direction of this result. Semantic types make the refresh guarantee stronger. They do not make it more complex, because the resolver is deterministic and its inputs are in the ChartSpec. Two runs of the resolver over one ChartSpec give one chart. This is the meaning of "bit-stable across runs" in pillar 3.

3.5 Where the validation puts the resolver

The primary result of the prototype was that validation cannot be one phase. The grammar checks run when the system reads a ChartSpec. Each check that needs the data runs later:

prototypes/chartspec-v1/chartspec_draft.py:452 and :529

    @model_validator(mode="after")
    def _validate_grammar(self) -> ChartSpec:          # phase 1 — the spec alone
        _check_mark_channels(self.mark.type, self.encodings, where="base")
        ...

def validate_against_profile(spec: ChartSpec, profile: dict) -> list[str]:
    """Phase 2. Returns error strings; empty list == passes."""   # needs profile.json

Semantic resolution needs the profile, because it needs the units, the domains, and the distributions. So it belongs in phase 2, beside the cardinality caps that are already there. There is no new phase and no new plumbing.

3.6 The real advantage — measurement is better than a guess

This part of the document is an argument, not a summary, so it needs a precise statement. Flint operates in a chat. It asks the model to select a semantic type, and it uses distribution methods for the gaps. chartagents runs DuckDB over the data before it calls the model.

Flint in a chatthe model guesses the type → distribution methods fill the gaps → compile
chartagentsthe DuckDB profile (cardinality, minimum and maximum, fraction or whole number, monotonic dates, currency-like ranges) → seeds and checks the guess of the model → resolver → compile

Figure 5. One resolver, better inputs. The claim of the document is parity and one addition. chartagents can measure the signals that Flint must guess. It can also use them to find a column that the model typed incorrectly.

Open question, stated in the document

How many of the 46 specific types can the profile identify alone, and how many still need a guess from the model? Nobody has measured this. The answer limits how much planning work the vocabulary really removes. It is one of four questions that the document sends to tickets.

3.7 Option B — use the Flint compiler, and the reasons to be careful

The second option is larger. It compiles a ChartSpec into the Flint input, and Flint then compiles that into a native chart. This gives Vega-Lite, ECharts, and Chart.js from one map. The team does not write three renderer adapters. The document gives this option medium confidence, and it uses most of its length on the costs.

CostWhat it means here
The language boundaryThe compiler with three backends is TypeScript. flint-py is a Python port, but it compiles Vega-Lite only. It is a source-only preview with no PyPI release. ECharts is the primary web output in the product document. To reach it, the team must add a Node sidecar to the sandbox, write a port, or wait for the roadmap of another team.
Grammar impedanceThe ChartSpec holds parts that the Flint input models differently: overlay layers with a list of permitted combinations (D5), typed annotations, interactions flags, and the escape marker for the custom-code rail. The map loses data in both directions. The team needs a capability matrix before it starts.
GovernanceFlint is a young research artifact with no published roadmap. The MIT license lets the team copy the parts into the repository. But that copy is a maintenance commitment. It is not a free solution.

The proposed shape of the experiment keeps it reversible. Flint becomes one adapter behind the CapabilityProfile boundary that the architecture already has. It declares a max_spec_version value, the same as each other adapter. The prototype already has the helper for that check:

prototypes/chartspec-v1/chartspec_draft.py:507–516

def adapter_supports(spec_version: str, adapter_max: str) -> tuple[bool, str]:
    s_major, s_minor = (int(p) for p in spec_version.split("."))
    a_major, a_minor = (int(p) for p in adapter_max.split("."))
    if s_major != a_major:
        return False, f"[{SpecError.SPEC_VERSION_UNSUPPORTED}] spec major {s_major} != adapter major {a_major}"
    ...

An adapter is a pluggable part. The team can add it or remove it without a change to the planner, the rail router, or the review loop. If Flint is an adapter, the team can still answer the question "was this a good decision?" at a later time.

3.8 The second file — what else is out there

The second document exists because of an uncomfortable fact in its own header. Flint became visible late, and the team nearly missed it. So the search covers six categories. Five entries have actions:

Draco / Draco 2 (UW)design knowledge as constraints

It states design guidelines as hard constraints, which remove incorrect encodings, and as soft constraints with learned weights, which put the other encodings in sequence. The document maps these onto two parts of chartagents.

chat2plotPython · MIT

The closest shipped precedent for the central bet: the language model emits a validated Pydantic or JSON spec, and not code. Its list of failures is a free set of valid-but-wrong ChartSpecs to test the validators against.

LIDA (Microsoft)agent pipeline, code generation

Summarize → goal → generate code → self-evaluate → repair. It is the good version of the design that the product document argues against. A reviewer will ask "how is this different from LIDA?", and the product document does not name it.

Vizro-AI → Vizro-MCPMcKinsey

The team stopped AI dashboard generation and moved back to charts only, plus an MCP server. Read this as a signal about scope discipline. It is also evidence that the field went to MCP first, and that chartagents went to an API first.

Evidence · Rill · MalloyBI as code

Durable specs with versions, and a cheap refresh. This is the pattern of pillar 6, and the market already validated it. State the difference clearly: a person writes their specs, and an agent writes the chartagents specs and the review gate checks them.

Spec Score · Vision Scoreevaluation

Named metrics for the benchmark in §11. Spec Score needs no judge and is deterministic. It is a structural answer to the self-preference risk of an LLM judge, which the product document already lists.

The Draco entry repeats the Flint argument most exactly, and it points at code that already exists. The channel contract for each mark in the prototype is a hand-written table of hard constraints:

prototypes/chartspec-v1/chartspec_draft.py:220–233

    "scatter": MarkRule(
        required=frozenset({"x", "y"}),
        allowed=frozenset({"x", "y", "color", "size", "facet", "tooltip"}),
        type_constraints={
            "x": frozenset({DataType.QUANTITATIVE, DataType.TEMPORAL}),
            "y": frozenset({DataType.QUANTITATIVE, DataType.TEMPORAL}),
            "size": _Q,
        },
    ),
    "pie": MarkRule(
        required=frozenset({"color", "y"}),
        allowed=frozenset({"color", "y", "tooltip"}),
        type_constraints={"color": _CAT, "y": _Q},

The hard constraints of Draco are the same idea. They are formal, and they are much more complete. Its soft constraints are the tier 1 lint gate in a different notation. Three examples are colorblind safety, cardinality caps, and the bar-baseline rule. The recommendation is small on purpose. Copy the model and the hard-and-soft taxonomy. Do not add an Answer Set Programming solver as a run-time dependency of a library that other teams embed.

What this page does not verify

Each statement above about the internals of Flint comes from the research document, and this page repeats it. This includes the 70 or more types, the counts in each tier, the five dimensions, the two compiler stages, the Vega-Lite-only preview status of flint-py, and the DirectVL benchmark margins. Nobody read an upstream source during the work on this page. The caveat in the document about LLM judge scores also applies to the benchmark table that it cites. Each statement about chartagents itself comes from a direct read of chartagents-prd.md and prototypes/chartspec-v1/chartspec_draft.py at the merge commit. The proposed Channel class in §3.1 is a summary of the prose in the document. That code is not in the repository.
