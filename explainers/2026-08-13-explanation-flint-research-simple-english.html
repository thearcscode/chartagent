1. Background — the rail, the ChartSpec, and the prompt

This section is the map. Section 2 is the idea. Section 3 is how the idea would sit in the pipeline. If this repository is new to you, four facts make the rest of the page easier to read.

The question of this page

A ChartSpec can be valid and still look poor. Validity is a grammar question. Look is a design question. Pull request #13 asks: where must the design knowledge live, so that a valid chart is also a good chart, and so that the answer does not depend on a prompt?

1.1 What chartagent must become

chartagent is a Python library. It gets a data source and an instruction, for example "monthly revenue by region, last two years". It then makes a finished chart. It operates behind an API. It does not operate in a chat window. A person embeds it in their own product. They do not chat with it.

The product document, chartagent-prd.md, has six pillars. Three of them apply here. Read each one as a constraint on Flint, not only as a product sentence:

  • Pillar 2 — the data stays in your infrastructure. Before the first call to the language model, the profiler reads the data with DuckDB. It writes a small profile.json file. That file holds the schema, the data types, the cardinality, the null rates, the minimum and maximum values, the percentiles, and some sample rows. The language model gets this metadata only. Section 3.6 uses this. Flint in a chat must guess many of those facts. chartagent can measure them.
  • Pillar 3 — reliability by design. The deterministic rail does most requests. The language model emits a ChartSpec, the system validates it, and trusted code draws the chart. There is no generated code on this path. A request that the grammar cannot express goes to the custom-code rail, where the language model writes Python or JavaScript in a sandbox. Design knowledge that lives in a prompt is not on this rail. It is a guess that can change.
  • Pillar 6 — make the chart one time, refresh it many times. A chart is a saved ChartSpec. To draw it again with new data, the system runs the stored transform block again and then calls the renderer adapter. There is no call to the language model, and the token cost is zero. Section 3.4 uses this. A method that reads the data again on each refresh can change the chart with no message.

The other three pillars still exist. This page does not need them. Pillar 1 is the output contract (ECharts JSON, Plotly, PNG, SVG, HTML). Pillar 4 is the review gate. Pillar 5 is the custom-code rail. Option B in section 3.7 touches pillar 1. The rest of this page is about pillars 2, 3, and 6.

1.2 What the ChartSpec is

The ChartSpec is the contract between the language model and the renderer adapter. It is a small grammar of graphics, and it is independent of any chart library. A runnable draft is at prototypes/chartspec-v1/chartspec_draft.py. That file has the mark PROTOTYPE — THROWAWAY. It holds nine numbered decisions, D1 to D9, and each decision exists for the team to examine.

This page needs two of those decisions later:

  • D2 — there is no aggregate field on a channel. Aggregation lives in the transform block. Section 3.3 returns to this.
  • D8 — None means inherit, never "off". Precedence is explicit spec value, then organization skill, then theme, then adapter default. Section 3.2 returns to this.

The change in this research is about the Channel class. A channel is one visual property of the chart, for example the x axis or the color:

prototypes/chartspec-v1/chartspec_draft.py:142–161

class Channel(BaseModel):
    model_config = ConfigDict(extra="forbid")
    field: str = Field(min_length=1)
    type: DataType
    title: str | None = None
    scale: ScaleSpec | None = None
    axis: AxisSpec | None = None
    sort: Literal["ascending", "descending", "none"] | str | None = None
    legend: bool | None = None  # color/size only; None => adapter default

The DataType class holds four values. They come from Vega-Lite:

prototypes/chartspec-v1/chartspec_draft.py:54–58

class DataType(StrEnum):
    QUANTITATIVE = "quantitative"
    TEMPORAL = "temporal"
    ORDINAL = "ordinal"
    NOMINAL = "nominal"

The four values classify how a column stores its values. They do not classify what those values mean to a person:

  • quantitative — a number. You can calculate a mean value from it. Revenue, temperature, and a rating of 1 to 5 are all quantitative.
  • temporal — a date or a time. A month column is temporal.
  • ordinal — categories in a known sequence. Small, medium, large is ordinal.
  • nominal — categories with no sequence. Region names are nominal.

That first bullet is the hole. Revenue, temperature, and a 1-to-5 rating share one data type. They do not share a format, an aggregation, a palette, or a zero baseline. Section 2 is about that hole.

Definition · grammar of graphics

A method to describe a chart as data columns that map onto visual channels, for example position, color, and size. It does not describe a chart as a sequence of drawing commands. Vega-Lite is the best known example. The ChartSpec is a smaller dialect of the same idea. Its size lets one team write a renderer adapter that supports all of it.

1.3 Where the design knowledge comes from today

This is the problem that the research examines. Look at two fields that the prototype already has:

prototypes/chartspec-v1/chartspec_draft.py:125–139

class ScaleSpec(BaseModel):
    ...
    zero: bool | None = None    # the bar-baseline lint (§7.3 T1) reads this

class AxisSpec(BaseModel):
    ...
    format: str | None = None   # a d3-format or strftime string

The scale.zero field records if zero has a meaning on this axis. The tier 1 lint in the review gate reads it. It then decides if a bar that starts above zero is a defect. The axis.format field holds a d3-format string, for example "$,.2s". The prototype declares both fields, and other code reads both fields. But no code in the library computes either field. They have one source only. The prompt tells the language model to supply them, and the model supplies them or does not.

A short example makes the cost visible. The user asks for a bar chart of monthly revenue. The grammar is happy with this ChartSpec:

{
  "mark": {"type": "bar"},
  "encodings": {
    "x": {"field": "month", "type": "temporal"},
    "y": {"field": "revenue_sum", "type": "quantitative"}
  }
}

That ChartSpec is valid. The chart that follows from it can still be wrong in three silent ways:

Missing factWhat a good chart doesWhat can go wrong
scale.zeroThe bars start at $0.The axis starts at $80,000. A $90,000 month looks twice as large as an $85,000 month. The grammar did not forbid this.
axis.formatThe ticks say $1.2M.The ticks say 1200000, or they say a date format. The field is a free string. The grammar cannot check it.
sum versus meanGroup by region with SUM.The planner averages revenue across regions. The number is legal. The story is false.

Three decisions that depend on meaning. The value quantitative is true for all three rows. It cannot select among them.

The conflict

Pillar 3 says that the design knowledge belongs in the library, because that makes the deterministic rail reliable. But each decision that depends on the meaning of a number depends on the prompt today. Four examples are currency format, percentage format, the choice between a sum and a mean value, and the choice between a sequential palette and a diverging palette. The value quantitative does not hold sufficient meaning to compute any of them. So the library declares the fields and then asks the model to be correct.

1.4 What arrived from outside

In July 2026, Microsoft Research and Renmin University released microsoft/flint-chart under the MIT license. It is an intermediate language for charts, and a compiler for that language. The research document reports its premise: low-level chart specs are long, weak, and easy to get wrong, and language models are bad at these specs. So the model must state the meaning, and a compiler must compute the low-level settings.

That premise is the same bet as pillar 3. The model fills a small form. Trusted code does the rest. Flint is the form-plus-compiler for "draw this spec well". chartagent is the system around that step.

A person found Flint at the same time as the team started to freeze the ChartSpec grammar. That is the reason for pull request #13. The pull request has two commits. The first commit (e5af358) is a deep read of Flint. The team nearly missed Flint, so the second commit (2a0b4b9) is a deliberate search for other libraries of the same class.

The pull request adds no product code. It adds two Markdown files. Nothing in the repository reads a Markdown file. The product of the work is a set of decisions that the team has not yet taken. Section 3 lists those decisions as Option A, Option B, and Option C.

Agree to this before you continue

Flint is not a competitor to chartagent. It occupies the layer under the deterministic rail, the layer that Figure 1 shows as unbuilt. The unique selling point of chartagent was never the renderer.

2. The idea — a column with the name revenue

The idea of this page is one sentence. The model names what a column means. Trusted code then decides how it looks.

Use the smallest possible example. A table has a column with the name revenue. The values are US dollars, and there is one row for each month. The user asks for a bar chart of the revenue by month. That example is small on purpose. It is enough to show the split.

Two different fields

Data type says how the computer stores the values. For revenue that value is quantitative. Semantic type says what the values mean to a person. For that column the value is Revenue. They are not the same field. Semantic type does not replace data type.

2.1 Today: the language model supplies the details

A valid chart only needs the map from columns to channels:

  • mark: bar
  • x: month, type temporal
  • y: revenue, type quantitative

That ChartSpec is legal. You already saw why in section 1.2. The four-value DataType class accepts it. A good chart also needs answers that quantitative cannot give:

QuestionGood answer for revenueWhy quantitative is not enough
Do the bars start at zero?Yes.Temperature is also quantitative, and zero is not always meaningful there.
How do we write the numbers?$1.2M, not 1200000.A count and a dollar amount look the same as numbers.
If we group rows, do we sum or average?Sum.You can add this month's revenue to last month's. You must not add two prices and call the result a price.

Today those answers live in the prompt. The planner must emit them as scale.zero and axis.format. Section 1.3 showed that the prototype declares those fields, and that no library code fills them.

Look at Figure 2 as a split of work, not as shorter JSON:

Today — the prompt must know this

{
  "mark": {"type": "bar"},
  "encodings": {
    "x": {"field": "month",
          "type": "temporal"},
    "y": {"field": "revenue_sum",
          "type": "quantitative",
          "scale": {"zero": true},
          "axis": {"format": "$,.2s"}}
  }
}

Proposed — the model states the meaning

{
  "mark": {"type": "bar"},
  "encodings": {
    "x": {"field": "month",
          "type": "temporal",
          "semantic": "Date"},
    "y": {"field": "revenue_sum",
          "type": "quantitative",
          "semantic": "Revenue"}
  }
}
// the resolver computes zero and format

Figure 2. One chart, two divisions of the work. On the left, the model is responsible for four presentation values, and each one can be wrong. On the right, the model is responsible for one word, Revenue. A resolver then computes the currency format, the default aggregation, and the zero baseline.

The string $,.2s is a d3-format string. It means "currency, with SI suffixes, two significant digits". Language models are weak at that kind of string. They are also free to forget zero: true. The chart is still valid. It is just worse.

The claim is not that the ChartSpec on the right is shorter. The claim is that it is easier to get correct. A model that has never read a d3-format string can still know that a column with the name revenue holds revenue. And when the library owns the computation, that computation is testable, a person can review it, and it gives the same result on each run. This is the meaning of the term "deterministic rail".

2.2 The mechanism: three tiers of vocabulary

There is an obvious objection. A vocabulary of seventy type names is a new method for the model to be wrong. The document reports the answer from Flint. The registry has three tiers, and each tier is a legal answer. The model does not need the most specific name. A less specific name is still useful:

Tier 0 · 6Families — Temporal, Measure, Categorical, and three more. They set the basic encoding strategy. A model can select one at a low cost.
Tier 1 · 17Categories — for example Measure divides into Amount, Physical, Proportion, and SignedMeasure. Each one has different aggregation and format behavior.
Tier 2 · 46Specific types — Revenue is not Price, because you can add revenue but you must not add a price. Temperature is not Quantity, because temperature can have a diverging midpoint.

Walk the same column down the ladder. The resolver reads tier 2, then tier 1, then tier 0. It stops at the tier that the model supplied:

  1. Say Revenue (tier 2). You get the currency format, a sum as the default aggregation, and a hint for a log scale.
  2. Say only Amount (tier 1). You still get the currency format and the sum. You lose the extra hints that only Revenue carries.
  3. Say only Measure (tier 0). You still get a quantitative encoding with a meaningful zero.
  4. Say a word that the registry does not know. You get the generic quantitative result. That is exactly today's ChartSpec.

The lowest result of the new system is the highest result of the old system. An unknown semantic type does not make the chart worse than a chart with no semantic type. The four values of DataType remain the floor.

The pair Revenue versus Price is the example to keep. Both are numbers. Both can use a currency format. They do not share an aggregation:

Revenue is additive

January revenue $10. February revenue $12. The total is $22. SUM is the correct hint.

Price is intensive

Widget A costs $10. Widget B costs $12. The "total price" is not $22. AVG is the correct hint. Or you weight by quantity. You do not add the prices.

One data type. Two semantic types. Two aggregation hints. Section 3.3 will say that a hint is not an authority. The transform block still holds the real aggregation.

Each semantic type carries five independent dimensions. This list is the list of prompt jobs that the proposal removes:

DimensionValuesWhat it decidesExample
Encoding candidatesa preference sequence over quantitative, ordinal, nominal, and temporalwhich DataType value to preferA date prefers temporal, not nominal.
Aggregation roleadditive · intensive · signed-additive · dimension · identifierSUM or AVG as the proposed defaultRevenue → SUM. Price → AVG.
Domain shapeopen · bounded · fixed · cyclicclamp limits, extrapolation, polar axesA clock is cyclic. A rating of 1 to 5 is bounded.
Diverging naturenone · conditional · inherenta sequential palette or a diverging paletteTemperature can need a midpoint. Quantity usually does not.
Format classcurrency · percent · unit-suffix · date, and morethe prefix, the suffix, and the precision in axis.formatRevenue → $,.2s. Share → percent.

Table 1. The five dimensions, as docs/research/flint-chart-leverage.md §1 reports them. Compare them with the fields in ScaleSpec and AxisSpec that no library code fills today. One data type was doing five jobs. It could not.

2.3 Why one column can need two different answers

A lookup table would say: Revenue always maps to these exact settings. That fails as soon as the channel changes. One detail explains why this is a resolver and not a lookup table.

Take a rating column with a domain of 1 to 5. The semantic type is the same in both charts below. The good answer is not the same:

On the x axis

Integer ticks at 1, 2, 3, 4, and 5. The position channel needs a scale with those ticks. A continuous axis that shows 1.7 is a worse answer.

On the color channel

A diverging palette with its midpoint at 3. Low ratings one color. High ratings the other color. Ticks of 1, 2, 3, 4, 5 are not the decision that color needs.

Same column. Same semantic type. Different visual job. Position and color are not the same channel, so they do not share one row in a lookup table.

So the compiler has two stages. Stage one computes the properties of the column: the format, the default aggregation, and the domain limits. It does not know which channel gets the column. Stage two changes those properties into decisions for one channel. First for each column, then for each channel. The inputs are semantic type and channel and mark.

2.4 The second claim: where Flint belongs

Section 2 is two claims together.

  • Claim 1 (sections 2.1 to 2.3). Meaning belongs in the spec. Polish is computed by code.
  • Claim 2 (this section). Flint is that computation layer. It is not a chartagent replacement.

Flint compiles a spec into a good native chart. That is the box in Figure 1 that the team has not built. Flint has no profiler, no planning loop, no review gate, no refresh guarantee, and no data source abstraction. Its MCP server also serves the single person in a chat window, and the product document lists that person as an explicit non-goal.

SystemQuestion it answers
Cortex AnalystWhich data?
FlintI have a spec. Draw it well.
chartagentI have data and an instruction. Select the spec, guarantee its quality, and refresh it for ever.
The model in one line

Flint stops at the exact point where the deterministic rail of chartagent starts to render. The document states it like this. Cortex Analyst answers "which data". Flint answers "I have a spec, draw it well". chartagent answers "I have data and an instruction, select the spec, guarantee its quality, and refresh it for ever".

Four sentences hold the whole of section 2. A column named revenue is quantitative in storage and Revenue in meaning. Today the model must also invent zero and $,.2s. Tomorrow it only has to say Revenue, and a resolver fills the rest, walking from specific types down to today's four-way fallback. Flint is that resolver-shaped layer. chartagent is everything around it.

3.1 At the planner boundary — a new field on Channel

Option A is the recommendation with the highest confidence. It does not need Flint code. It needs one new field on the class you saw in section 1.2:

proposed — docs/research/flint-chart-leverage.md §3

class Channel(BaseModel):
    field: str
    type: DataType                    # no change — the 4 Vega-Lite values stay
    semantic: str | None = None       # NEW: "Revenue" | "Amount" | "Measure" | ...
    annotation: SemanticAnnotation | None = None   # intrinsicDomain / unit / sortOrder
    scale: ScaleSpec | None = None    # the resolver can now fill this
    axis: AxisSpec | None = None      # the resolver can now fill this
    ...

Note what the proposal does not do. The DataType class stays. The semantic type is beside it, and the semantic type is optional. So each ChartSpec that is valid today stays valid. A missing semantic field is the generic quantitative result from section 2.2. That is the floor.

The annotation object holds the facts that a type name alone cannot give. Three examples follow. Each one is a fact about this column in this data set, not a fact about the type Rating or Temperature in general:

FactWhy the type name is not enoughWhat the annotation holds
The domain of a rating is 1 to 5.Some ratings are 1 to 10. Some are 0 to 100.intrinsicDomain: [1, 5]
The unit is °C, not USD.Physical and Amount both format numbers. They do not share a unit.unit: "°C"
The category sorts small, medium, large.Alphabetical order gives large, medium, small. That order is wrong.sortOrder: ["small", "medium", "large"]

The type name selects the family of rules. The annotation fills the holes that only this data set can fill. Section 2.3 needed the domain [1, 5] to put the color midpoint at 3. That number is not inside the word Rating.

You can ship a small vocabulary first

The team does not need all 46 specific types on day one. The tiered fallback means the team can ship tier 0 and tier 1, and grow tier 2 later. An unknown name still lands on today's DataType.

3.2 Between the profile and the render — the resolver

The second half of Option A puts the computed values into the chart. The proposal puts a resolver between profile.json and the renderer adapter. Then, and this is the important detail, the proposal refuses to invent a new precedence rule for it. The prototype already fixed a precedence rule in decision D8:

prototypes/chartspec-v1/chartspec_draft.py:399–410

class Style(BaseModel):
    """
    D8: every field is Optional and None means INHERIT, never "off".
    Precedence at render time: explicit spec value > org skill > theme > adapter default.
    """

Read D8 as four layers, from the top. The first layer that has a value wins. Empty means "look at the next layer". Empty does not mean "turn this off". The ChartSpec lesson already uses this rule for style. Option A uses the same rule for format, zero, and palette.

The values from the semantic type become the adapter default layer. That layer is the floor, not the ceiling:

Explicit value in the ChartSpec — the planner wrote format: "$,.0f"wins
Organization skill — "always show revenue in thousands"then
Theme — the house stylethen
Adapter default — computed from the semantic typefloor ← new

Figure 3. Option A adds a source of values. It does not add a rule about them. A ChartSpec that sets no value gets good defaults. A value that an organization or a planner states explicitly still wins, which is what D8 already promises.

Walk the revenue bar chart through those four layers:

  1. The resolver sees semantic: "Revenue" on y. It proposes axis.format: "$,.2s" and scale.zero: true. That is the floor.
  2. If the house theme says "use a comma as the thousands separator", the theme can replace the format string. The zero baseline stays.
  3. If the organization skill says "always show revenue in thousands", that skill replaces the format again. The ticks now say $1,200k.
  4. If this one ChartSpec writes "format": "$,.0f", that explicit value wins. The planner asked for whole dollars with no suffix. The resolver does not fight it.

If the computed values sat above the explicit values, nobody could state an exception. That is why they sit on the floor. Quiz question 2 tests this.

The invariant stays true

In this grammar, None has the meaning inherit in each position. Decision D9 removes each None from the canonical JSON form. So a resolver that fills the empty fields at render time cannot change what a stored ChartSpec says. Patch mode continues to compare the ChartSpec that the planner wrote. It does not compare the resolved ChartSpec. Two people can still diff two saved specs and see only what the planner stated.

3.3 Against D2 — a hint, not an authority

Aggregation is the most probable failure of this proposal. The Flint types carry an aggregation role. A reader can think: "then the channel now holds SUM or AVG, and that breaks D2." D2 is an explicit ChartSpec decision. It forbids aggregate on a channel:

prototypes/chartspec-v1/chartspec_draft.py:143–151

    D2: NO `aggregate` on the channel — unlike Vega-Lite.

    Encodings reference *output columns of the transform block*. Aggregation lives in
    `data.transform` (issue #4) because (a) pushdown compiles the transform to the
    source's SQL and cannot reach into encodings, and (b) zero-cost refresh (§7.7)
    re-runs the transform alone. Encoding-level aggregate would fork that boundary.

Vega-Lite writes the sum on the encoding. The ChartSpec does not:

Vega-Lite — aggregate on the channel

{ "y": { "field": "revenue",
         "aggregate": "sum" } }

ChartSpec — aggregate in the transform

{ "data": { "transform": {
    "group_by": ["month"],
    "aggregate": {
      "revenue_sum": "sum(revenue)"
    } } },
  "encodings": {
    "y": { "field": "revenue_sum",
           "type": "quantitative",
           "semantic": "Revenue" } }
}

The encoding still points at a column that already exists. The new semantic field does not add aggregate: "sum" to that encoding.

The document gives a distinction with a real result. The aggregation role is a default that seeds the transform planner. Revenue proposes SUM, and Price proposes AVG. The planner can accept the hint and write sum(revenue) into the transform block. The planner can also reject the hint, if the instruction is "average revenue per store". The data.transform block stays the only source of truth about the computation.

No code in the render path or the pushdown path reads an aggregation from a channel. So the boundary that D2 protects stays intact. That boundary makes the transform block a self-contained thing that compiles to SQL and that the system can run alone on a refresh. Quiz question 1 tests this. The correct answer is authority, not location and not time.

3.4 Against pillar 6 — freeze the inference at plan time

There is a less obvious hazard, and the document finds it. Flint computes a missing semantic type from the distribution of the data. For example, if 80% of the absolute values in a column are 1 or less, Flint reads a percentage as a fraction (0.34 means 34%) and not as a whole number (0.34 means 0.34%). That method is acceptable in a chat. The person sees the chart and can say "wrong". It is dangerous with a refresh guarantee. Nobody is watching.

If the inference runs again on each refresh

The data for January: 92% of the values are 1 or less. Flint reads a fraction. The axis shows 34%.

The data for February moves to 61%. Flint reads whole numbers. The same chart now shows 0.34%. There is no error and no call to the language model. The chart is different, and nothing reports it.

Pinned at plan time

The inference runs one time, during the planning step. The system writes the result into the ChartSpec as an annotation, for example unit: "fraction".

Each refresh replays the stored decision. New data cannot change the reading, because no code reads it again. If the schema itself changes, that is a different error, and SchemaDriftError exists to make it loud.

Figure 4. Why the document says that the system must freeze a distribution-based inference into the ChartSpec. Pillar 6 promises that a refresh is a replay. A method that runs again on new data breaks that promise, and it gives no warning. Quiz question 4 tests this.

The cost of the inference is not the problem. The method is a data method. It does not call the language model. A refresh could run it at zero token cost. The problem is stability. The same saved ChartSpec must draw the same kind of chart when the rows change.

Note the direction of this result. Semantic types make the refresh guarantee stronger. They do not make it more complex, because the resolver is deterministic and its inputs are in the ChartSpec. Two runs of the resolver over one ChartSpec give one chart. This is the meaning of "bit-stable across runs" in pillar 3.

3.5 Where the validation puts the resolver

The primary result of the ChartSpec prototype was that validation cannot be one phase. The grammar checks run when the system reads a ChartSpec. Each check that needs the data runs later. You can find a histogram with a y channel with no data. You cannot find 830 colors on sku without profile.json.

Semantic resolution needs the profile, because it needs the units, the domains, and the distributions. A type name of Rating is not enough. The resolver also needs to know that this rating runs from 1 to 5. That fact is in the data. So resolution belongs in phase 2, beside the cardinality caps that are already there.

There is no new phase and no new plumbing. The resolver sits in the phase that already reads profile.json.

3.6 The real advantage — measurement is better than a guess

This part of the document is an argument, not a summary, so it needs a precise statement. Flint operates in a chat. It asks the model to select a semantic type, and it uses distribution methods for the gaps. chartagent runs DuckDB over the data before it calls the model. Pillar 2 already paid for that profile. Option A can spend it a second time.

Flint in a chatthe model guesses the type → distribution methods fill the gaps → compile
chartagentthe DuckDB profile (cardinality, minimum and maximum, fraction or whole number, monotonic dates, currency-like ranges) → seeds and checks the guess of the model → resolver → compile

Figure 5. One resolver, better inputs. The claim of the document is parity and one addition. chartagent can measure the signals that Flint must guess. It can also use them to find a column that the model typed incorrectly.

A concrete check. The model says semantic: "Date" on a column. The profile says the values are not monotonic, and the cardinality is 4. The library can reject that guess before the resolver runs. Flint in a chat has a weaker version of this check, because it often sees only the rows that the user pasted.

Open question, stated in the document

How many of the 46 specific types can the profile identify alone, and how many still need a guess from the model? Nobody has measured this. The answer limits how much planning work the vocabulary really removes. It is one of four questions that the document sends to tickets. Do not treat "the profile can do all of it" as a fact. It is a hope.

3.7 Option B — use the Flint compiler, and the reasons to be careful

Option A is a field and a resolver. The team can take it without running Flint. Option B is larger. It compiles a ChartSpec into the Flint input, and Flint then compiles that into a native chart. This gives Vega-Lite, ECharts, and Chart.js from one map. The team does not write three renderer adapters.

The document gives this option medium confidence. The upside is real. The costs are also real. Most of the section is the costs, because a reader who only sees the upside will treat Flint as "the renderer" and lock the architecture too early.

CostWhat it means hereWhat a spike must answer
The language boundaryThe compiler with three backends is TypeScript. flint-py is a Python port, but it compiles Vega-Lite only. It is a source-only preview with no PyPI release. ECharts is the primary web output in the product document. To reach it, the team must add a Node sidecar to the sandbox, write a port, or wait for the roadmap of another team.Is Vega-Lite quality from flint-py good enough to justify the next step?

Quiz question 3 tests the language boundary. The obstacle is not Playwright. The obstacle is that ECharts from Flint lives in TypeScript today.

The proposed shape of the experiment keeps it reversible. Flint becomes one adapter behind the CapabilityProfile boundary that the architecture already has. It declares a max_spec_version value, the same as each other adapter. The prototype already has the helper for that check:

prototypes/chartspec-v1/chartspec_draft.py:507–516

    a_major, a_minor = (int(p) for p in adapter_max.split("."))

An adapter is a pluggable part. The team can add it or remove it without a change to the planner, the rail router, or the review loop. If Flint is an adapter, the team can still answer the question "was this a good decision?" at a later time. The spike is single-mark only: bar, line, scatter, heatmap. Overlays and the custom-code escape marker wait.

Option B is not Option A

The team can adopt semantic types and never run the Flint compiler. The team can also spike the compiler and later remove it. Do not bundle the two decisions. The document ranks them separately for that reason.

3.8 The second file — what else is out there

The second document exists because of an uncomfortable fact in its own header. Flint became visible late, and the team nearly missed it. So the search covers six categories. None of these systems occupy the full chartagent position (embeddable Python API, data in infrastructure, deterministic rail first, review gate, zero-token refresh). Several own a piece well enough to steal from, or to be measured against.

Five entries have actions. Read each card as "what to do before development", not as "what to depend on":

Draco / Draco 2 (UW)design knowledge as constraints

It states design guidelines as hard constraints, which remove incorrect encodings, and as soft constraints with learned weights, which put the other encodings in sequence. The document maps these onto two parts of chartagent.

chat2plotPython · MIT

The closest shipped precedent for the central bet: the language model emits a validated Pydantic or JSON spec, and not code. Its list of failures is a free set of valid-but-wrong ChartSpecs to test the validators against.

LIDA (Microsoft)agent pipeline, code generation

Summarize → goal → generate code → self-evaluate → repair. It is the good version of the design that the product document argues against. A reviewer will ask "how is this different from LIDA?", and the product document does not name it.

Vizro-AI → Vizro-MCPMcKinsey

The team stopped AI dashboard generation and moved back to charts only, plus an MCP server. Read this as a signal about scope discipline. It is also evidence that the field went to MCP first, and that chartagent went to an API first.

Evidence · Rill · MalloyBI as code

Durable specs with versions, and a cheap refresh. This is the pattern of pillar 6, and the market already validated it. State the difference clearly: a person writes their specs, and an agent writes the chartagent specs and the review gate checks them.

Spec Score · Vision Scoreevaluation

Named metrics for the benchmark in §11. Spec Score needs no judge and is deterministic. It is a structural answer to the self-preference risk of an LLM judge, which the product document already lists.

Draco is the closest cousin of Option A

The Draco entry repeats the Flint argument most exactly, and it points at code that already exists. The channel contract for each mark in the prototype is a hand-written table of hard constraints. A histogram must not have y. A pie has no x. Scatter is the only mark with size:

The hard constraints of Draco are the same idea. They are formal, and they are much more complete. Its soft constraints are the tier 1 lint gate in a different notation. Three examples are colorblind safety, cardinality caps, and the bar-baseline rule. Quiz question 5 tests this pair: grammar validators ≈ hard constraints, lint gate ≈ soft constraints.

The recommendation is small on purpose. Copy the model and the hard-and-soft taxonomy. Do not add an Answer Set Programming solver as a run-time dependency of a library that other teams embed. Clingo is heavy. The catalog is the useful part.

chat2plot and LIDA are two answers to "is this already built?"

chat2plot already ships the ChartSpec bet in miniature: the model emits JSON, a renderer draws it, Pydantic checks the shape. Read its failure list. Those failures are valid specs that still draw the wrong chart. That is the input the phase-1 and phase-2 validators must catch.

LIDA is the whole agent pipeline, with a repair loop. It generates library code. That is the design that pillar 3 rejects. The difference to state in the product document: chartagent runs a deterministic rail first, and only escapes to generated code for the minority. A reviewer will ask "how is this not just LIDA?". The product document does not name LIDA today. That is a gap in positioning, not a gap in the architecture.

Vizro and BI-as-code are signals, not dependencies

Vizro stopped AI dashboard generation. A funded team narrowed to charts plus MCP. That supports the chartagent scope (charts, not dashboards). It also shows that the field went MCP-first. chartagent went API-first on purpose. The product document should now argue that choice, because the rest of the field went the other way.

Evidence, Rill, and Malloy prove that the market already believes in durable specs and cheap refresh. Pillar 6 is not a novel gamble. The delta is authorship. A person writes a Rill spec. An agent writes a ChartSpec, and the review gate checks it. Then both refresh the same way.
